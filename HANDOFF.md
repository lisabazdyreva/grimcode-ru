# Рабочие документы лежат в ветке `working-docs`

**Решение владельца 1 сентября 2026.** Пять документов вне кода — `NOTES.md`, `HANDOFF.md`,
`ONBOARDING.md`, `MODULE-CALLS.md`, `ENV-VARS.md` — запушены снимком в ветку
[`working-docs`](https://github.com/lisabazdyreva/grimcode-ru/tree/working-docs) (`5c076b8`), чтобы не
жили только на диске виртуалки. Владелец на время переключается на другой проект.

**Что важно про эту ветку:**

- она **без родителя** и содержит **только эти пять файлов**, ни строчки кода. Вливать её никуда не
  надо и нельзя — она не работа, а хранилище;
- в рабочей ветке `module-independence` документы **по-прежнему вне git**, как и договаривались. Значит
  ничего «убирать перед следующим коммитом» не требуется: они там и не появились. Правило
  «никогда `git add -A`» действует ровно как раньше;
- документы на диске — главная копия. Ветка от них отстаёт с момента снимка.

**Обновить снимок** (когда документы заметно продвинулись). Ветка перезаписывается новым сиротским
коммитом, без родителя, — история снимков не нужна:

```bash
IDX=$(mktemp) && rm -f "$IDX" && GIT_INDEX_FILE="$IDX" git update-index --add -- \
  NOTES.md HANDOFF.md ONBOARDING.md MODULE-CALLS.md ENV-VARS.md && \
  TREE=$(GIT_INDEX_FILE="$IDX" git write-tree) && \
  git branch -f working-docs $(git commit-tree $TREE -m "Рабочие документы: снимок") && \
  git push --force-with-lease fork working-docs
```

`--force` здесь законен и безопасен: ветка своя, кода в ней нет, история снимков ценности не имеет.
Это единственное место в проекте, где перезапись ветки разрешена.

**Достать файл из снимка, не переключаясь:** `git show working-docs:NOTES.md`.

# Правила прямо сейчас

**Коммитить можно, по одному шагу и с явными путями.** Никогда `git add -A`: рабочие документы вне git
намеренно. Сообщение — одна строка по существу плюс
`Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>`. Владелец не против `--amend`, если правка
относится к последнему коммиту.

**`AGENTS.md` ведёт агент целиком, включая раздел «Директивы».** Но правку правила по существу решает
человек: агент предлагает формулировку и называет её в отчёте, молча не меняет. `HUMAN-INTENT.md` —
файл владельца, агент туда не пишет и не создаёт его.

**Часто просит сократить — и каждый раз права.** Сказано «длинно» — резать, а не защищать написанное.
Отвечать коротко: сначала вывод обычными словами, потом причина. «Не поняла» — сигнал переписать проще,
а не повторить то же другими словами.

**Спрашивает «а это точно так?» — значит перепроверить, а не подтвердить.** За две сессии это трижды
меняло дело: у находки причина оказывалась серьёзнее, выигрыш — в десять раз меньше, а собственная
формулировка про corepack — шире, чем проверено. Цену называть измеренным числом.

**Замечания по интерфейсу приходят скриншотом, и за каждым стоит настоящая ошибка.** Смотреть на свой
экран глазами, а не только на зелёные тесты.

**Свои креды владелец предлагала — брать не нужно.** Всё видно на разовой копии со своим владельцем.

**Не откатывать файлы через `git checkout`, пока работа не закоммичена** — так уже терялась готовая
правка. И осторожно с `Write` по существующему файлу.

# Форма, к которой пришли

Модуль с внутренней поверхностью отдаёт одну фабрику. Она не принимает ни пула, ни логгера — только
соседей, а окружение приезжает вторым источником, на `c.env`:

```ts
export function createModule() {                     // соседей нет — значит и аргументов нет
  const database = createDatabase();                 // ленивый пул, запомненное обещание
  const repository = async (env: EmailEnv) => new EmailRepository(await database(env));

  const internalCaller = (env: EmailEnv, _call: { requestId: string }): EmailInternalCaller =>
    withDeadlineOn(
      createInternalCallerFactory(async () => ({ repo: await repository(env) })),
      'email',
      RPC_TIMEOUT_MS,
    );

  const app = createServiceApp<EmailEnv>('email');
  // …монтирования…
  return { app, internalCaller };
}

export type EmailInternalCaller = ReturnType<typeof createInternalCallerFactory>;
```

`requestId` в аргументе остался, хотя писать его больше некуда: он приходит в заголовке, возвращается
в ответе и связывает один запрос в разных модулях.

Пять решений, за которые заплачено разбором и зондами. Не пересматривать без причины:

1. **Одна фабрика, а не две.** Иначе пул и транспорт создаются дважды.
2. **Вызывающий объект строит монтирование, а процедура получает готовый.** Исключение одно — gateway
   строит его в ветке `/admin/**`, потому что видит весь трафик процесса.
3. **Объект делается на каждый запрос** и принимает `requestId`.
4. **Срок ожидания ставит модуль, а не место вызова** — `withDeadlineOn` в `shared/src/rpc.ts`.
5. **Тип вызывающего объекта назван явно** через `ReturnType<typeof createInternalCallerFactory>`. Без
   аннотации `tsc` отказывается писать `.d.ts` (`TS2742`), проверено зондом.

**Что проверено зондами и обязано ломаться:** срок в 1 мс у любой фабрики даёт `RpcTimeoutError`,
событие уходит в `failed`, а регистрация всё равно отвечает 200. Сломанный вход `authorize` даёт 503, а
не 200, — ветка fail-closed. Сломанный вход `getIdentitiesByIds` красит ровно один тест приёмки.
Внутренний путь `/internal/rpc` не отвечает нигде.

# Как проверять

```bash
pnpm check          # линт, типы, юнит-тесты, сборка, пять скриптов-проверок
pnpm dev            # собрать изменённое и запустить процесс на GATEWAY_PORT
pnpm test:acceptance
pnpm test:browser
```

**Наборы против стенда ветки не пойдут** — владелец панели там человек, пароля у агента нет. Гонять
второй копией со своим слагом:

```bash
nohup env PROJECT_SLUG=probe1 GATEWAY_PORT=63099 PUBLIC_SITE_URL=http://127.0.0.1:63099 \
  DATABASE_URL='postgres://template:template@127.0.0.1:63003/postgres' \
  EMAIL_PROVIDER=log EMAIL_FROM_ADDRESS=no-reply@example.com EMAIL_FROM_NAME=Template \
  AUTH_SESSION_TTL_SECONDS=2592000 PORT_RANGE_START=63000 PORT_RANGE_END=63020 \
  node dist/index.js > лог 2>&1 &
```

Запуск в подшелле иногда умирает молча — брать `nohup env …`, как здесь. Все три обязательных значения
в команде уже есть: без слага, адреса или порта процесс теперь не поднимется, а скажет, чего не хватает.
Дальше завести своего владельца: `POST /service/auth/rpc/register`, тот же адрес в `/service/auth/rpc/login` с
`-c cookies.txt`, затем `POST /admin/rpc/session` — в ответе должно быть `"role":"owner"`. Наборы берут
адрес из `ACCEPTANCE_BASE_URL`, креды из `ACCEPTANCE_OWNER_EMAIL` и `ACCEPTANCE_OWNER_PASSWORD`, и им
нужен ещё `PROJECT_SLUG` копии — иначе две проверки ищут базы по слагу из `.env` и краснеют.

Убирать за собой: гасить **по pid из `ps -eo pid,args`** (`pkill -f "dist/index.js"` попадает и в стенд
ветки) и сносить свои пять баз `DROP DATABASE <слаг>_<модуль>`.

**Смотреть экран раздела базы** — так же: своя копия, свой владелец, логин через форму playwright'ом,
дальше `page.goto('/admin/database')` и работать внутри `page.frameLocator('iframe')`.

# Метод, коротко

Целиком в `NOTES.md`, двадцать пунктов. Главное: читать код, а не грепать; числа считать, а не
прикидывать; проверку ломать намеренно и смотреть, что краснеет именно она; свои свежие правки
перечитывать отдельным проходом; найденное записывать, а не чинить молча. За владельцем не проверять.
Когда решение произнесено — выполнять.

И то, что подтвердилось этой сессией дважды:

**Один греп — не проверка.** Логгеры я объявила удалёнными трижды, и трижды находился хвост: мёртвый
импорт типа в файле, который не проверяется типами; целый механизм в `pg-interface`; два теста этого
пакета, опиравшихся на него. Каждый раз находил следующий греп, заданный иначе.

**Файл, который никто не запускает, врёт молча.** Unit systemd пять дней указывал на удалённый пакет, и
ни одна проверка этого не видела — нашлось случайно, когда владелец спросила про сам файл. Отсюда
правило: если что-то не проверяется ни тестом, ни скриптом, у него надо либо завести проверку, либо
признать его непроверенным вслух — а лучше не держать вовсе, как и решили с деплоем.
