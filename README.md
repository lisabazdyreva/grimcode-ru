# Модульный шаблон с админкой для вайбкодинга Grimcode

Заготовка продукта, у которой скучная часть уже сделана: публичный сайт, приложение с входом по логину, админка с правами доступа и почта с редактором писем.
Всё это уже работает вместе — дальше на этой основе делается ваш продукт.

Внутри — восемь модулей в одном процессе: отдельные пакеты, своя база у каждого, кто хранит данные, общение только через контракты. Разделены они по-настоящему, просто запускаются вместе: модуль не может ни импортировать соседа, ни открыть его базу.

Единственный файл в проекте, который должен редактировать человек — это `DIRECTIVES.md`. ИИ агентам строго запрещено редактировать этот файл.
В этом файле прописана архитектура проекта, ключевые требования и правила (директивы), которые агентам нельзя нарушать.

## Первый запуск

Перед запуском нужно создать файл .env на основе .env.example, в котором достаточно изменить только `PROJECT_SLUG` —
техническое имя проекта: строчные латинские буквы, цифры и подчёркивания, не длиннее 49 символов.
После этого просто попросите агента запустить проект. Первый запуск займёт несколько минут, последующие быстро.

Локально проект запускается на порту 63000 (главная ветка).

## Работа с ветками

Рекомендуется работать через агентов — Claude Code или Codex — на VPS или виртуалке.
Новый чат = новый worktree (оба агента умеют), каждая ветка запускается на своём свободном порту в диапазоне 63001–63020.

При первом запуске проекта в новом worktree агент копирует переменные окружения (файл .env) и базу данных.
Так агенты работают параллельно и не мешают друг другу.

## Админка

Первый зарегистрированный аккаунт становится владельцем админки.
Зарегистрируйтесь в приложении (/app) и откройте админку (/admin) — и вы станете админом.

## База данных

При локальной разработке база данных — PostgreSQL на самой машине, один сервер на все копии проекта. В каждой рабочей ветке создаётся копия баз данных: разделяет их слаг в именах.

У каждого модуля с базой своя база данных, и создаёт он её себе сам при первом запросе. Отдельных ролей и паролей больше нет — учётная запись одна, поэтому чужую базу модуль не откроет не из-за отказа PostgreSQL, а из-за собственной сверки: открыв соединение, он проверяет, что попал именно в свою базу, и иначе не работает. Баз пять: у `app`, `gateway` и `site` их нет вовсе.

В продакшне база данных должна подниматься отдельно, а строка подключения указывается в переменной окружения DATABASE_URL.

## Письма

Локально письма никуда не уходят, а сохраняются в логах и доступны для просмотра из админки сервиса Email.

На продакшне нужно переключить `EMAIL_PROVIDER` с `log` на `unisender` и указать ключ от Unisender Go — одного ключа не хватит, при `log` письма продолжат складываться в журнал и никуда не уйдут. Или попросите агента настроить любой другой почтовый сервис.
