Шаблон проекта: сайт, приложение и админ-панель, восемь модулей в одном процессе и пять баз данных.
Здесь — что где лежит, куда идёт запрос, откуда берутся настройки и по каким правилам части общаются
между собой. Составлено 31 августа 2026.

## 1. Главная идея

Это не одно приложение, а восемь отдельных пакетов, которые запускаются одним процессом и почти ничего
не знают друг о друге.

Обычно «разделить на части» делают, чтобы потом растащить части по разным серверам. Здесь цель другая:
**правка должна оставаться в границах одного модуля.** Когда модуль правит нейросеть, она работает
именно в этом модуле — а не во всём проекте сразу: ей незачем и нечем задеть остальное.

Из этой цели вытекает почти всё остальное устройство, и её стоит держать в голове, читая дальше. У
каждого модуля своя папка, свои таблицы в своей базе и своя объявленная поверхность — то, что он
согласился делать для других.

Способов дотянуться до соседа у модуля нет: импортировать его код, открыть его базу, прочитать
настройки, узнать его адрес — всё это либо запрещено правилом, либо просто невозможно. И запреты не на
словах: шесть скриптов в `pnpm check` краснеют, если правило нарушено. Границу держит проверка, а не
аккуратность того, кто правит.

### Словарь на первое время

- **Модуль** — папка в `modules/`, она же отдельный пакет.

- **Точка сборки** — корневой файл `index.ts`, который собирает всё вместе.

- **Шлюз** — модуль `gateway`, единственный вход в приложение. Подробнее в разделе 5.

- **Миграция** — записанный запрос, который создаёт или меняет таблицы.

- **Пул** — набор готовых соединений к базе.

- **Процедура** — одна операция модуля с именем: `login`, `getProfile`, `sendEmail`. По сути эндпоинт: у
  неё описано, что она принимает и что возвращает. Процедуры — единственный способ **попросить модуль
  что-то сделать**, и пользуются им и браузер, и соседний модуль.

- **tRPC** — библиотека, на которой сделаны процедуры. Делает две вещи, и их стоит различать. Во время
  работы **проверяет значения**: у каждой процедуры объявлены `.input(…)` и `.output(…)` — пришло не то,
  отказ; вернулось не то, ошибка. Сами схемы обычно лежат в `schemas.ts` модуля, а у процедуры стоит
  ссылка на них. А при сборке tRPC даёт зовущему **типизированного клиента**: вызов чужой процедуры
  выглядит как вызов функции, и опечатку в имени или неверный аргумент ловит компилятор.

## 2. Локальный запуск

Три команды, и больше ничего запускать не нужно:

```bash
pnpm install
cp .env.example .env
pnpm dev
```

Ни базы, ни таблицы создавать руками не надо: **каждый модуль создаёт свою базу и накатывает свои
миграции сам** — при первом запросе, который до него доходит. Отдельного шага «подготовить базу» в
проекте нет вовсе.

`pnpm dev` — это сборка и запуск одной командой: отдельного режима «запускать исходники» здесь нет,
локально проект тоже работает из собранного. Поэтому после каждой правки кода команду дают снова —
собирается только изменившееся, это секунды.

Дальше открываете адрес из `PUBLIC_SITE_URL`: `/` — сайт, `/app/` — приложение, `/admin` — панель.

**Первый, кто зарегистрируется, становится владельцем панели** — про роли подробнее в разделе 5.

Единственное, что нужно на машине заранее, — PostgreSQL и учётная запись с правом создавать базы:

```bash
sudo apt install postgresql
sudo -u postgres createuser --createdb --pwprompt template
```

## 3. Карта файлов

Файлов много, но важных — десятка полтора. Остальное либо повторяется от модуля к модулю, либо
генерируется.

### Файлы в корне проекта

| Файл | Зачем он |
| --- | --- |
| `index.ts` | **Точка сборки, самый важный файл проекта.** Читает окружение, создаёт модули, выдаёт каждому настройки и способ позвать соседа, открывает порт. Единственный файл, которому разрешено знать все пакеты, — и потому в нём нет решений, только порядок вызовов |
| `AGENTS.md` | Директивы — правила проекта словами: как всё устроено и чего делать нельзя. Читать до кода |
| `HUMAN-INTENT.md` | Замысел владельца. Старше всех остальных документов; заводит и правит только человек. **Файла пока нет** |
| `.env` | Настройки этой копии проекта: имя проекта, порт, адрес базы, способ отправки писем. Программа читает их при запуске |
| `.env.example` | Тот же файл с заполненным примером — его копируют в `.env` |
| `package.json` | Команды (`dev`, `check`, наборы проверок) и зависимости корня |
| `pnpm-workspace.yaml` | Список папок, которые pnpm считает пакетами этого проекта: `modules/*`, `shared`, `pg-interface`, `tests`. Поэтому установка одна на всех, а свои пакеты берутся из соседней папки, а не скачиваются |
| `turbo.json` | План задач для turbo — того, кто запускает сборку и тесты по пакетам. Что от чего зависит, что задача создаёт и что поэтому можно взять из кэша вместо повторной работы |
| `docs/` | Документация: архитектура, локальный запуск, точка сборки, устройство панели, доступ в админку |
| `scripts/check-*.mjs` | Шесть проверок, которые держат правила. Про них — раздел 9 |

### Файлы внутри модуля

Раскладка одинаковая у пяти модулей с базой — `auth`, `users`, `admin`, `notifications`, `email`: узнав
один, знаете все. У остальных трёх её часть просто не нужна. У `app` есть только точка входа и `web/`;
у `gateway` — одна точка входа; а `site` устроен иначе всех: браузерная часть в `src/`, сервером служит
рукописный `server/index.mjs` — единственный файл в проекте, который компилятор не видит.

| Путь | Что внутри |
| --- | --- |
| `src/index.ts` | Функция, которая создаёт модуль |
| `src/contract.ts` | Что модуль показывает соседям — только типы |
| `src/env.ts` | Чего модуль ждёт от точки сборки — тип без значений |
| `src/routers/` или `routers.ts` | Сами процедуры и схемы их входа и выхода |
| `src/db/database.ts` | Единственное место, где модуль открывает свою базу |
| `src/db/migrations/` | Файл на версию плюс `index.ts` со списком |
| `src/repository.ts` | Все запросы к своим таблицам в одном месте |
| `web/` | Браузерная часть, если она есть |
| `web/src/api.ts` | Клиенты tRPC этой браузерной части: с какими модулями она разговаривает |
| `README.md` | Описание модуля — первое чтение перед правкой |

Пять из них стоит пояснить.

**`src/index.ts`** — по имени функции видно, зовут ли модуль соседи. `createApp()` значит «только отвечает
на запросы» (`site`, `app`, `gateway`, `users`). `createModule()` — «до меня ещё и дотягиваются соседи»
(`auth`, `admin`, `email`, `notifications`): такая функция возвращает и приложение, и способ позвать этот
модуль, а раздаёт его точка сборки.

**`src/contract.ts`** — тип роутера и типы данных, из которых у соседа собирается типизированный клиент.
Схем проверки здесь нет и быть не может: схема `zod` — это значение, а наружу уезжает только выведенный
из неё тип. Поэтому после сборки файл пустой: `export {}`.

**`src/routers/`** — процедуры разложены по уровню доверия: `public` доступны снаружи, `internal` только
соседям, `admin` — из панели. Рядом с каждой стоят схемы, по которым проверяются значения.

**`web/src/api.ts`** — здесь создаются клиенты, по одному на модуль, с которым эта часть говорит.
Файл отвечает на вопрос «с кем она вообще разговаривает»: у приложения это `auth` и `users`, и больше
никто. Правила, общие для всех вызовов, — прикреплять ли куку, прикладывать ли токен CSRF — заданы здесь
один раз, а не на каждом экране. Есть у всех шести модулей с папкой `web/`.

**`src/db/database.ts`** — создаёт базу, сверяет, что открылась своя (`SELECT current_database()` против
выданного имени), и накатывает миграции.

Не совпало — модуль отказывается работать, и увидите вы это так: запрос к нему отвечает 500 с текстом
`Pool opened database "postgres", expected "app_auth"`, а процесс печатает ту же строку в свой вывод.
Проверено на копии, которой подсунули чужой адрес базы. Обратите внимание: **процесс при этом жив** —
сайт отвечает, отказывает только тот модуль, чья база не сошлась.

### Два пакета, которые не модули

**`shared/`** — общий инструментарий, которым можно пользоваться всем: работа с окружением, куки,
CSRF, применятель миграций, запись файла миграции, сроки вызовов, тема оформления. Ничего
продуктового и никаких хранилищ здесь нет — они принадлежат модулям.

**`pg-interface/`** — интерфейс для работы с базами данных: тот самый раздел «База данных» в панели.
Список таблиц, страница строк с фильтрами и сортировкой, правка строк и колонок. Заменил стороннюю
программу, которую панель раньше открывала в рамке. Написан так, чтобы его можно было опубликовать
отдельно: **из нашего репозитория он не импортирует ничего**, всё нужное получает аргументами.

Создаёт его точка сборки — [`index.ts:110`](index.ts:110), передавая пять строк подключения и способ
записать миграцию. Дальше шлюз отдаёт ему всё, что приходит на `/admin/embed/database`, — но только
после проверки, что пришёл владелец.

## 4. Модули и их назначение

Восемь модулей. У пяти есть своя база данных, у трёх — нет.

| Модуль | За что отвечает | База |
| --- | --- | --- |
| `gateway` | Единственный вход в приложение: принимает каждый запрос и решает, какому модулю его отдать. Он же и единственное место, где проверяется право войти в админку | нет |
| `site` | Публичный сайт — то, что видит любой посетитель по `/` | нет |
| `app` | Приложение для пользователя на `/app/`: экраны входа, регистрации, восстановления пароля и своего профиля. Серверная половина только отдаёт собранный бандл; процедуры `auth` и `users` зовёт уже браузер | нет |
| `auth` | Вход и доверие: кто это и действительна ли его сессия. Держит личности, пароли (только хеши), сессии, одноразовые токены и счётчик неудачных попыток | есть |
| `users` | Продуктовая сторона пользователя — то, что о нём знает приложение, в отличие от входа. В шаблоне это одно отображаемое имя: место, куда проект дописывает свои поля | есть |
| `admin` | Права в панели: кто администратор, к каким разделам его пустили, что он делал. Отвечает на вопрос «кто это и что ему можно», а применяет ответ `gateway` | есть |
| `notifications` | Развязка между «что-то случилось» и «кому-то надо сообщить»: принимает событие от модуля и решает, во что оно превращается. Пока — в письмо | есть |
| `email` | Всё про письма: шаблоны с версиями, отправка и журнал доставок. Отправляет либо настоящим провайдером, либо локально, когда письмо никуда не уходит | есть |

## 5. Путь запроса

### Кто встречает запрос

Порт у процесса один, а модулей восемь. Значит, кто-то должен встречать каждый входящий запрос и
решать, кому его отдать. Это и есть шлюз — модуль `gateway`.

Он делает ровно две вещи. **Смотрит на начало пути и выбирает получателя:** `/app/…` — приложению,
`/admin/…` — панели, `/service/…` — публичным процедурам, всё прочее — сайту. **И проверяет права на
вход в админку** — один раз, за всех.

Почему проверка живёт там, а не в каждом модуле: если бы каждый проверял сам, забытая проверка в одном
месте открыла бы дырку во всём. А так забыть негде — мимо шлюза не проходит ничего.

Сам он ничего не хранит и своей базы у него нет.

### Владелец и администратор

В панели две роли, и разница между ними важнее, чем кажется.

**Администратор** — тот, кому выдали доступ к отдельным разделам. Доступ выдаётся по сервисам:
можно пустить в почту и не пускать в пользователей. Такая выдача называется грантом.

**Владелец** — тот, кому доступно всё, и грантов ему не нужно. Владельцем становится **первый
зарегистрировавшийся в приложении**: специальной кнопки «назначить владельца» нет. Отсюда правило,
о котором стоит помнить, поднимая копию в сети, которой не доверяете: регистрируйтесь сразу.

**Раздел базы данных — только владельца.** Не потому, что он опаснее прочих, а потому, что смотрит в
данные всех модулей сразу. Гранта на него нет вовсе: [authorization.ts:65](modules/admin/src/authorization.ts:65)
отвечает отказом любому, кто не владелец. Раздать нечего — значит нельзя раздать по ошибке.

### Куда идёт запрос

Снаружи проект выглядит как один адрес и один порт. Внутри — шлюз, который смотрит на начало пути и
отдаёт запрос дальше.

```
                    ┌─────────────── один процесс node, порт из GATEWAY_PORT ──────────────┐
                    │                                                                      │
  браузер  ──http──▶│  gateway ──── /              ──▶ site                                │
  один адрес        │  (шлюз)  ──── /app/**         ──▶ app                                │
                    │          ──── /admin/**       ──▶ admin                             │
                    │          ──── /admin/embed/database ──▶ pg-interface                  │
                    │          ──── /service/*/rpc  ──▶ auth · users                        │
                    └──────────────────────────────────────────────────────────────────────┘
```

Ветка `/admin/**` отличается от остальных: только она проходит проверку прав, и делает это шлюз —
включая картинки и стили панели, для них отдельного правила нет. Модуль `admin` отвечает на вопрос
«кто это и что ему можно», а дальше шлюз сам решает, кому отдать запрос: страницы панели — модулю
`admin`, а `/admin/embed/database` — сразу разделу базы. Панель через себя его не пропускает.

Публичных процедур снаружи доступно ровно две группы: `auth` и `users`. Остальные модули по сети
извне недостижимы — их зовут либо через админку, либо соседи напрямую.

### Внутри процесса сети нет

Модуль похож на маленький сервер: принимает запрос, возвращает ответ. Но порта у него своего нет — порт
один на весь процесс.

Поэтому, когда шлюзу нужен модуль, он **вызывает его функцию** и передаёт ей тот самый запрос, что
пришёл от браузера. Ответ возвращается как из любой функции. Никакой отправки, никакого второго
соединения: запрос внутри процесса — обычная переменная, которую передают дальше.

Из этого следуют две вещи, заметные во всём проекте.

**Адресов модулей нет нигде.** Их некому и незачем адресовать — вызывают напрямую. Строку вида
`http://localhost:3001` в проекте не найти.

**Модуль не знает, кто его позвал** — браузер через шлюз или сосед. Он видит запрос и отвечает. Отсюда,
кстати, лёгкость проверки: в тесте модулю просто передают запрос, сервер поднимать не нужно.

**И одно, что часто спрашивают: зачем тогда всё выглядит сетевым?** Затем, что эта форма не даёт модулю
прирасти к соседу. Дверь у него одна и та же — и для браузера, и для соседнего модуля, — а другой не
появляется.

**Как понять, что несколько вызовов — это один запрос.** У запроса есть номер, он едет в заголовке
`x-template-request-id`: пришёл снаружи — берётся оттуда, не пришёл — заводится новый. Дальше номер
передаётся во все вызовы, которые этот запрос за собой потянул, и возвращается в ответе. Логов в
проекте нет, так что это единственное, чем связать «человек зарегистрировался» и «ушло письмо».

## 6. Путь настройки

Настройки лежат в `.env` и доходят до модуля по одной дороге. Правило здесь одно: **модуль не читает
окружение сам** — значения ему выдаёт точка сборки.

```
  .env  ────▶  index.ts  ────▶  AuthEnv, EmailEnv, UsersEnv…  ────▶  модуль
                  ▲                                                     │
                  └──────────────────── запрещено ──────────────────────┘
```

- **`.env`** — текстовый файл со строками вида `ИМЯ=значение`. Читает его node при запуске: в команде
  `pnpm dev` для этого стоит `--env-file=.env`. Значения оказываются в окружении процесса раньше, чем
  начнёт работать `index.ts`.
- **`index.ts`** — точка сборки. Разбирает прочитанное и собирает по объекту настроек на каждый модуль.
- **`AuthEnv`, `EmailEnv`, `UsersEnv`** — настройки одного модуля. Внутри значения, а не имена
  переменных: модуль не может ни прочитать чужую настройку, ни угадать имя новой.
- **модуль** — видит свой объект на `c.env`, внутри запроса. При прямом вызове соседа запроса нет, и
  тот же объект подаёт точка сборки аргументом вызова.
- **запрет проверяется** — модулю нельзя читать окружение самому: ни `process.env`, ни `requireEnv`, ни
  файл. Нарушение ловят линтер и `check-boundaries`, поэтому договорённостью это не держится.

### Что такое `c.env`

Модули написаны на Hono — библиотеке, на которой держатся их приложения. Когда шлюз вызывает модуль, он
передаёт два аргумента: запрос и объект настроек этого модуля.

```ts
apps['users'].fetch(request, usersEnv);
```

Внутри модуля этот объект и называется `c.env`. Читают из него по имени поля: `c.env.databaseUrl`.
Обратите внимание — не `DATABASE_URL`: **имён переменных окружения модуль не знает вовсе**, он знает
только поля, которые ему положили. Чужого поля там нет, и написать его не получится.

Вне запроса `c.env` не существует. Отсюда одна особенность, заметная в коде: пул к базе создаётся не при
старте, а на первом запросе — раньше модулю просто нечем.

### Что именно получает каждый модуль

Не имена переменных, а готовые значения — имени `DATABASE_URL` модуль не знает вовсе.

| Модуль | Что ему выдают |
| --- | --- |
| `admin`, `notifications`, `users` | `databaseUrl` — строка подключения к своей базе; `databaseName` — имя этой базы, чтобы сверить, что открылась она; `maintenanceUrl` — адрес сервера для единственного `CREATE DATABASE` |
| `auth` | то же самое плюс `sessionTtlSeconds` — сколько живёт сессия |
| `email` | то же самое плюс `mail` — способ отправки и данные отправителя |
| `site`, `app`, `gateway` | ничего: `{}`. Своей базы у них нет, а всё прочее приходит с запросом |

Обратите внимание: **имя базы выдаётся отдельной строкой, а не выковыривается из адреса.** Это и есть
то, чем модуль потом сверяет открытую базу с ожидаемой.

### Четыре обязательных значения

Три из них не имеют умолчаний нарочно: программа откажется стартовать и назовёт пропущенное. Угаданное
значение здесь ломает тихо — потому и не угадывают.

| Переменная | Что решает |
| --- | --- |
| `PROJECT_SLUG` | Имена баз и куки. Не длиннее 49 символов `[a-z0-9_]` |
| `PUBLIC_SITE_URL` | Адрес, каким его видит посетитель. Из него строятся ссылки в письмах, от его схемы зависит признак `Secure` у куки |
| `PORT` или `GATEWAY_PORT` | Где слушать. `PORT` ставит платформа развёртывания, `GATEWAY_PORT` позволяет держать две копии рядом |
| `DATABASE_URL` | Сервер и одна учётная запись. Имя базы каждый модуль подставляет своё |

Остальное необязательно: срок сессии, способ отправки писем и его настройки, диапазон портов для новых
веток, отдельные адреса баз для отдельных модулей. Полный список — в `docs/local-development.md`.

## 7. Вызовы между модулями

К процедуре модуля ведут два разных пути.

**Из браузера — через адрес.** Роутер модуля смонтирован на путь, например `/service/auth/rpc`. Приходит
запрос, tRPC разбирает его тело, находит процедуру по имени, проверяет вход схемой и зовёт. Настройки
модуль берёт с `c.env`.

**От соседа — без всякого запроса.** Точка сборки выдаёт модулю *вызывающий объект*: готовый способ
позвать процедуры соседа. Внутри он устроен средствами самой tRPC — процедура зовётся обычным вызовом
функции, с обычным объектом на входе. Ни адреса, ни тела запроса, ни разбора: настройки соседу были
поданы, когда этот объект создавали.

**Общее у двух дорог — роутер и схемы.** Процедура одна и та же, проверка входа и выхода одна и та же,
кто бы ни звал.

**А различие даёт то, что важнее всего для безопасности.** Роутеры разложены по уровню доверия, и
внутренний **не смонтирован ни на один путь**. Поэтому `resolveSession` снаружи недостижим не потому,
что закрыт правами, — а потому, что как адрес не существует вовсе. Забыть закрыть его нельзя: нечего
закрывать.

Вот как выглядит цепочка при регистрации:

```
                  index.ts
    │                 │                 │
    ▼                 ▼                 ▼
   auth  ────▶  notifications  ────▶  email
```

- **`index.ts`** выдаёт каждому из трёх модулей вызывающий объект — способ позвать того, кто ему нужен.
  Сами модули друг друга не находят.
- **`auth`** при регистрации зовёт `notifications`: «случилось вот такое событие».
- **`notifications`** решает, во что событие превращается, и зовёт `email` отправить письмо.
- **у каждого вызова свой срок ожидания** — 10 секунд. Ставит его тот модуль, которого зовут, а не тот,
  кто зовёт: иначе один медленный сосед растянул бы весь запрос.
- **если не дошло вовремя** — вызов падает по сроку, но регистрация всё равно отвечает 200, а событие
  уходит в «не доставлено». Пользователь зарегистрирован, письмо не ушло.
- **типы соседа** каждый берёт из `@template/<имя>/contract`. Кода оттуда не приходит: после сборки этот
  файл пустой.

**Три правила, которые тут легко нарушить.** Импортировать соседа нельзя — ни код, ни даже типы, кроме
подпути `contract`. Открывать чужую базу нельзя — ни подменой имени в своей строке подключения, ни
сборкой строки самому. Отказ соседа нельзя проглатывать молча: если вход не проверился, ответ должен
быть отказом, а не «всё хорошо». Все три проверяются скриптами, а последнее — ещё и зондами: сломанный
вход в `authorize` обязан давать 503, а не 200.

### Разбор одной процедуры — можно пропустить при первом чтении

Панель узнаёт, кто пришёл, спрашивая у `auth`. Тот же путь целиком, на одной процедуре.

**Объявлена в `auth`** — [`routers/internal.ts:33`](modules/auth/src/routers/internal.ts:33):

```ts
resolveSession: t.procedure
  .input(z.object({ sessionToken: z.string().min(1).max(400) }))
  .output(z.object({ identity: identitySchema.nullable() }))
  .query(async ({ input, ctx }) => { … }),
```

Принимает непустую строку не длиннее 400 символов, возвращает личность или `null`. Обе схемы работают во
время работы программы: пустая строка — отказ, и код процедуры даже не начнётся.

Лежит она в `internal`-роутере, а он не смонтирован ни на один путь. Поэтому снаружи её не позвать: не
«закрыта правами», а не существует как адрес.

**Наружу уезжает только тип** — в `auth/contract.ts` одна строка `export type { AuthInternalCaller }`.
Это форма: какие есть методы, что принимают и возвращают. При сборке она стирается.

**Способ звать выдаёт точка сборки** — [`index.ts:143`](index.ts:143): панель получает `callAuth` и
больше ничего про `auth` не знает.

**Вызов** — [`admin/authorization.ts:38`](modules/admin/src/authorization.ts:38):

```ts
const { identity } = await deps.auth.resolveSession({ sessionToken: input.sessionToken });
```

Обычный вызов метода, без сети и без адреса.

**Кто что проверил:** компилятор — что метод есть и аргумент того типа (это из типа в контракте);
программа во время работы — что строка непустая и не длиннее 400 (это из схемы внутри `auth`).

## 8. Базы данных

Баз пять — по одной на модуль, который хранит данные. Имя каждой складывается как
`<PROJECT_SLUG>_<модуль>`, поэтому две копии проекта на одном сервере PostgreSQL не мешают друг другу.

| База | Таблицы | Что в них |
| --- | --- | --- |
| `<слаг>_auth` | `identities`, `sessions`, `auth_tokens`, `auth_audit` | Личности с хешами паролей, живые сессии, одноразовые токены (тоже хешами) и журнал событий входа |
| `<слаг>_users` | `profiles` | Профиль — по сути отображаемое имя. Ссылки на личность в базе нет: связь описана договором, а не ключом |
| `<слаг>_admin` | `administrators`, `administrator_grants`, `admin_audit` | Кто администратор, к каким сервисам ему выдан доступ, что он делал. Ключ у грантов составной — из двух колонок |
| `<слаг>_notifications` | `events` | Событие, кому оно адресовано и чем кончилось: `accepted`, `routed` или `failed`, плюс ссылка на доставку и текст отказа |
| `<слаг>_email` | `templates`, `template_versions`, `deliveries`, `email_audit` | Шаблоны писем с версиями и журнал доставок — со снимком того, что было отправлено |

### Как база появляется

```
  первый запрос ──▶ создать базу ──▶ сверить имя ──▶ накатить миграции ──▶ держать пул
  к этому модулю    если её нет      та ли открылась   только недостающие
```

Сверка стоит раньше миграций нарочно: сначала убедиться, что открылась своя база, и только потом
менять в ней схему.

**`schema_migrations` — наша таблица, а не механизм PostgreSQL.** У самого PostgreSQL никакой памяти о
миграциях нет: он знает только, что в базе есть сейчас, а как к этому пришли — не помнит. Поэтому
применятель миграций (сотня строк в `shared`) заводит эту таблицу сам, по одной в каждой базе модуля.
Имя расхожее — так её называют многие инструменты, — отсюда и обманчивое ощущение, что она встроенная.

Внутри по строке на применённую версию: номер, имя и отпечаток текста запроса. Поэтому новая база строится с первой версии, существующая получает только новое, а повторный
запуск не делает ничего.

Отдельного шага «подготовить базу» нет: этим занимается сам модуль, лениво. Цена названа прямо — плохая
миграция ответит ошибкой первому пользователю, а не остановит развёртывание.

**Зато процесс поднимается, даже если база не работает.** Порт откроется, `/healthz` ответит, сайт
будет отдаваться; откажут только те модули, которым нужны данные, — каждый сам по себе. Проверено:
копия с недостижимой базой отвечала 200 на сайте и приложении и 500 на регистрации. Так вышло из
той же лени: базу открывают на первом запросе, а не при старте, поэтому упавшая база мешает не всему
приложению, а той части, которая в неё полезла.

> **Ловушка на всю жизнь проекта.** Применённая миграция запоминается **отпечатком своего текста**.
> Поправить выпущенный файл — даже выровнять отступы — значит остановить модуль на любой базе, где эта
> версия уже применена: он откажется работать и назовёт версию. Исправление всегда одно — **новая
> версия**.

### Раздел «База данных» в панели

В панели есть свой просмотр баз — `pg-interface`. Он доступен только владельцу, потому что смотрит
сразу во все базы. Кроме чтения и правки строк он умеет добавлять колонки, а также переименовывать и
удалять те, **которые сам же и добавил**. Колонки, пришедшие из миграций модуля, он не трогает: их код
модуля читает по имени, и переименование сломало бы его на первом же запросе.

Важная деталь, если будете этим пользоваться: **такая правка становится обычной миграцией модуля**. В
проекте появляется файл, его нужно закоммитить — и тогда колонка приедет к сотруднику сама. Там, где
исходников рядом нет, правка схемы с экрана недоступна вовсе.

## 9. Проверки

Одна команда, и она обязана быть зелёной:

```bash
pnpm check
```

Внутри: линтер, типы, юнит-тесты, настоящая сборка и шесть скриптов, каждый из которых держит правило,
словами описанное в директивах.

### Что значит «защита от чужого сайта»

Браузер посылает куки автоматически — в том числе если запрос отправил другой сайт, куда вы случайно
зашли. То есть чужая страница может послать запрос от вашего имени, и сессия к нему приложится сама.
Защита от этого простая: изменяющий запрос должен принести **что-то, чего чужая страница знать не
может.**

В панели это `x-csrf-token`: приложение выдаёт токен, кладёт его в куку и требует тем же значением в
заголовке. Чужой сайт куку прочитать не может, а значит и заголовок подделать нечем.

У раздела базы свой заголовок — `x-pg-interface`. Причина не в надёжности, а в том, что проверка
`check-procedures` умеет читать только процедуры tRPC, а этот пакет не они: он бы оказался не покрыт
ничем. Поэтому защиту он держит сам и сам же её проверяет своим тестом.

| Скрипт | Что не пропустит |
| --- | --- |
| `check-dependencies` | Пакет, объявивший соседа или драйвер базы там, где его быть не должно |
| `check-boundaries` | Импорт соседнего модуля, пул вне отведённого файла, чтение окружения из модуля, открытие порта где-либо кроме точки сборки |
| `check-procedures` | Процедуру без описанного выхода; изменяющую админскую процедуру без защиты от чужого сайта; роутер, который **ни смонтирован на путь, ни выдан вызывающему объекту** — то есть достижим способом, которого проверка не видит. Внутренние роутеры не смонтированы нарочно, и это законно: их выдают соседям |
| `check-migrations` | Файл миграции, который лежит в папке и не попал в список, — его никто никогда не применит; повтор или пропуск версии; имя, разошедшееся с содержимым |
| `check-service-ids` | Сервис, известный шлюзу и невидимый в панели, или наоборот |
| `check-scripts` | Команду, названную как команда pnpm: `pnpm up` запустил бы обновление зависимостей вместо проекта |

### Два набора против работающего приложения

Они лежат отдельным пакетом — `tests/`, и в отличие от `pnpm check` им нужно уже поднятое приложение:
они стучатся в него снаружи, как человек из браузера.

- `pnpm test:acceptance` — проверки по HTTP, 59 штук;
- `pnpm test:browser` — проверки настоящим браузером, 42 штуки.

Что им надо передать: адрес приложения (`ACCEPTANCE_BASE_URL`), почту и пароль владельца панели
(`ACCEPTANCE_OWNER_EMAIL`, `ACCEPTANCE_OWNER_PASSWORD`) и `PROJECT_SLUG` той копии, против которой
гоняете, — иначе две проверки будут искать базы по чужому слагу и покраснеют не по делу. В `.env` этих
переменных нет: они не про запуск проекта, а про его проверку.

## 10. Где легко ошибиться

Все случаи настоящие, каждый однажды стоил времени.

**Слаг длиннее 49 символов.** PostgreSQL молча обрезает имена до 63 байт. При длинном слаге два модуля
могут получить одно имя базы и начать делить данные. Программа ловит худший случай на старте,
остальные — нет.

**Правка сервера без перезапуска.** Файлы экрана читаются с диска на каждый запрос, а серверные
маршруты — нет. Отсюда знакомое «кнопка есть, а сервер отвечает 404»: экран новый, процесс старый.
После правки серверной половины процесс нужно перезапустить.

Обратное тоже стоит знать: **правку экрана перезапускать не надо.** Пересобрали — обновите страницу, и
всё. А у вёрстки сайта есть даже живая перезагрузка, отдельной командой `vite dev` в модуле `site`.

**Локальные письма не отдают ссылку.** При локальном способе отправки письмо складывается в журнал
доставок — но одноразовый токен из ссылки в журнале нарочно затирается, а само письмо никуда не
уходит. Значит ссылку восстановления пароля локально получить нельзя. Это известная поломка, она
записана; пароль меняется в обход почты.

**Кэш сборки может оказаться общим.** Кэш turbo лежит в корне копии проекта, а рабочие ветки в этом
проекте живут внутри главной копии — поэтому кэш у них общий с ней. Проверить «собирается ли с нуля» из
ветки не получится, пока не отказаться от кэша явно.

**Наборы проверок против чужого экземпляра.** Две проверки приёмки ищут базы по имени и берут слаг из
окружения — запуск против копии с другим слагом краснеет не по делу. А две браузерные правда добавляют
колонки, то есть пишут миграции в исходники: копии для них нужно отвести отдельное место, иначе каждый
прогон оставит файлы в репозитории.

## 11. Где что решается

В этом проекте у каждого вида решения есть своё место, и это не «в коде».

**`HUMAN-INTENT.md` — замысел.** Что человек хочет от продукта, включая архитектурные решения. Старше
всего остального; правит только человек. Файла пока нет, и его появление — первое, чего проект ждёт.

**`AGENTS.md`, раздел «Директивы» — правила.** Каким проект есть и чего делать нельзя. Описания ведёт
агент, но правку правила по существу решает человек: агент предлагает формулировку и называет её
вслух, молча не меняет.

**`docs/` — описание для человека.** Архитектура, локальный запуск, точка сборки, устройство панели,
доступ в админку.
Поддерживать в актуальном состоянии — обязанность агента.

**README модуля — описание модуля.** Подробно и по делу про одно место. Первое чтение перед правкой
незнакомого модуля.

**`NOTES.md` и `HANDOFF.md` — рабочая память.** Вне git, намеренно. В первом — метод работы,
особенности этой машины, решённое с доводами и измеренными числами. Во втором — где мы сейчас и что
осталось.
