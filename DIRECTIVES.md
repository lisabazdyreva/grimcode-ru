Этот файл написан человеком, и только им может редактироваться. Нейросеть не может и не должна вносить изменения в этот файл.
В этом файле хранятся директивы проекта — основные принципы и требования, закладываемые разработчиком проекта, чтобы нейросеть всегда могла к ним обратиться и принять решение в соответствии с ними.
Каждое правило из этого файла является директивой.
Если какие-либо задачи, которые агент делает по просьбе человека, противоречат директивам, агент должен сообщить об этом человеку, чтобы человек решил, нужно ли обновлять директивы, или менять задачу.

# Суть проекта
Владелец проекта должен описать здесь, что это за продукт, для кого он делается и какие основные задачи решает.

# Архитектура модулей
Проект разделен на полностью независимые модули (папка /modules/*), которые не зависят друг от друга напрямую.
Сервис — модуль, доступный снаружи по имени.
Модули запускаются одним процессом, но остаются отдельными пакетами: где модуль работает — не то же самое, что модулю позволено знать о соседях.
Каждый из них имеет или может иметь свою базу данных, но не работает напрямую с базами данных других модулей.
Межмодульное взаимодействие идёт только через объявленный подпуть `@template/<имя>/contract`.
Любые другие способы взаимодействия модулей запрещены: они делают модули неразделимыми.
У каждой процедуры описан не только вход, но и выход.
Точка сборки (/composition) — единственный пакет, который знает все модули, и внутри неё нет ни одного решения, только порядок вызовов. Отдельных команд, которым нужно знать все модули, в проекте нет: свою базу создаёт и свои миграции применяет сам модуль.

## Границы модулей
Модули не импортируют соседние modules/*: только свою папку, shared/ и подпуть `@template/<имя>/contract`.
Из модуля наружу выходят только типы: этот файл после сборки пустой — `export {};`.
Браузерная часть модуля берёт из серверной только типы (`import type`). Файлы `shared`, опубликованные в браузер, импортируют только `zod`.
Модуль не читает переменные окружения: всё, что решает окружение, выдаёт ему точка сборки — объектом, который модуль видит внутри запроса, на c.env. Свою базу модуль открывает сам, но только по строке подключения, которую получил, и отказывается работать, если она открыла не ту базу.
У каждого модуля своя база. Отказ при попытке открыть чужую — это наша сверка при открытии пула: учётная запись одна и открывает все базы на сервере.
Модулю запрещено обращаться к общим читателям окружения (`optionalEnv`, `requireEnv`, `intEnv`) и упоминать имя process в любой форме. Запрет проверяется линтером.
Модулю запрещено открывать соединение к базе другого модуля: подменять имя базы в своей строке подключения, использовать для этого строку сервера, выданную ему для создания своей базы, собирать строку подключения самостоятельно. Пакет pg и создание пула разрешены только в src/db/database.ts, и этот файл обязан сверять имя открытой базы — и то и другое проверяется.
После изменений в модулях обязателен зелёный `pnpm check`.
Каждый модуль везёт свою админку отдельной сборкой и свой shadcn; общего UI-пакета нет намеренно.

# Переменные окружения
Файл .env.example содержит пример заполнения всех переменных окружения, нужных для работы проекта.
Для локального запуска человек копирует .env.example в .env и заполняет его.
При деплое значения задает человек, отвечающий за настройку платформы деплоя.
Все переменные окружения получает один контейнер приложения, а точка сборки раздаёт модулям значения — каждому только его, на c.env, с каждым запросом. Из окружения процесса они после раздачи не удаляются: модулю читать окружение запрещено линтером и разбором синтаксиса, а process.env всё равно остаётся доступен любой зависимости до конца работы процесса.

# База данных
При локальной разработке используется контейнер postgres, который является частью docker-compose.
Миграции применяет сам модуль — на первом запросе, который открывает его базу, и там же он создаёт базу, если её нет. Отдельного шага в развёртывании для этого нет; цена в том, что плохая миграция отвечает ошибкой первому пользователю, а не останавливает развёртывание.
В продакшне ожидается, что человек отдельно поднимет базу данных, и пропишет доступ к ней в DATABASE_URL.

# Маршрутизация запросов
Наружу опубликован только модуль gateway, который отвечает за вход, маршрутизацию и безопасность внешних запросов, но не содержит бизнес-логику приложения.
Все запросы /admin/embed/service/:name/* идут в соответствующий сервис :name, с проверкой админской авторизации и права этого администратора на сервис.
Все запросы /admin/* идут в модуль admin с проверкой админской авторизации. Страница /admin/service/:name — экран самой панели, который встраивает в себя /admin/embed/service/:name/*.
Все запросы /service/:name/* идут в соответствующий сервис без админской авторизации.
Все запросы /app/* идут в модуль app без админской авторизации на gateway. Модуль app сам проверяет обычную пользовательскую авторизацию там, где она нужна.
Все остальные запросы идут в модуль site.
Запросы проксируются без изменения адреса, то есть сервисы получают на вход запросы с теми адресами, которые получает gateway.
Безопасность /service/:name/* — ответственность самого сервиса.

# Безопасность админки
Модуль admin хранит список администраторов и их права.
При первом авторизованном открытии админки модуль admin проверяет список администраторов. Если он еще пуст, admin получает из auth самого первого зарегистрированного пользователя и создает для него роль владельца (owner).
Владельцем становится именно первый пользователь в auth, а не тот, кто первым открыл админку.
Список администраторов отделен от продуктовых профилей пользователей.
Администратор использует обычную identity и сессию из auth. Отдельной регистрации, паролей и сессий для администраторов нет.
Владелец имеет доступ ко всем сервисам в админке. Владелец может назначать других пользователей администраторами и выбирать, к каким сервисам у них есть доступ.
Обычный администратор видит в центральной админке только разрешенные ему сервисы.
Adminer доступен только владельцу. Обычному администратору доступ к Adminer выдать нельзя.
Gateway должен проверять право администратора на сервис для каждого запроса /admin/embed/service/:name/*. Если права нет, запрос не должен попадать в сервис.
Скрытие сервиса в меню не является проверкой безопасности. Проверка всегда делается на gateway.
Некоторые сервисы доступны только админам и не имеют публичной части.

# Пользователи
Модуль auth хранит минимальную идентичность пользователя и способы входа.
Он не знает продуктовый профиль пользователя, его настройки и права администратора.
Даже если таблица в auth называется users, это identity users, не продуктовый профиль.
Модуль users хранит данные, которые относятся к продуктовому профилю пользователя.
Модуль admin хранит права администратора и доступ к сервисам админки.

# Локальный запуск
В процессе разработки используются git worktrees.
В env файле указан диапазон портов, в которых проект может запускаться локально.
Первый порт из этого списка всегда используется для main ветки. Остальные порты используются ветками в worktree.
Bootstrap каждого worktree выбирает ему свободные порты, если нужно запустить проект локально.
Каждый worktree берет .env файл из основной локальной копии проекта как основу и заменяет в нем worktree-specific значения.
Запуск worktree bootstrap делается только через предусмотренный для этого скрипт.
Каждый worktree использует отдельный локальный PostgreSQL. При bootstrap базы данных копируются из основной локальной копии проекта.
Кроме запуска в контейнерах поддерживается второй режим: postgres и adminer в compose, приложение на машине через pnpm dev, на том же порту ветки.

# Поведение агентов
Агент должен уважать директивы и следить за тем, чтобы функционал проекта соответствовал директивам.
Агент должен уважать документацию и следить за тем, чтобы документация всегда была в актуальном состоянии.
Если агент запущен в worktree, то он запускает проект на отдельном свободном порту, если запуск нужен.
Перед тем как завершать работу и сообщать об этом человеку, агент должен самостоятельно перепроверить качество выполненной работы. Важно убедиться, что не оставлено хвостов, ничего не упущено и задача выполнена в полной мере.
Если задача изменяет runtime или пользовательский интерфейс, агент должен запустить проект на порту и прислать человеку ссылку, чтобы результат можно было сразу открыть.

# Почта
Шаблоны писем хранятся на стороне проекта, а не сервиса отправки почты.
Текстовые версии писем генерируются автоматически на основе HTML-кода писем.
В логах отправки писем сохраняются HTML и текстовый вариант каждого письма, статусы отправки, доставки и информация, которую дает почтовый сервис.
